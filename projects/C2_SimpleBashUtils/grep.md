# Описание утилиты

**grep** (от англ. _Global Regular Expression Print_) — это консольная утилита в Unix/Linux, которая ищет в тексте строки, соответствующие заданному шаблону, и выводит их.

**grep** выводит **целиком** совпавшую строку, то есть если в строке совпала только часть, выведется вся строка всё равно:

```file1.txt
apple
Apple
applepen other text
banana brain
app
```

```bash
cat file.txt | grep "apple"

apple
applepen other text
```

Ищет именно совпадения **подстроки**, а не совпадение всего слова:
```bash
cat tests/data/file1.txt | grep "ap"

apple
applepen other text
app and other text
```

## Ключевые принципы `grep`

1. **Построчная обработка**: `grep` читает входные данные (файл или стандартный ввод) **строка за строкой**. Он не анализирует весь текст целиком, а проверяет каждую строку на соответствие шаблону.
    
2. **Поиск по подстроке**: По умолчанию `grep` ищет шаблон **как подстроку** внутри строки. Это значит, что шаблон `кот` будет найден и в строке `кот`, и в `который`, и в `котлета`. Если вам нужно найти слово целиком, используйте флаг `-w` (целое слово) или `-x` (вся строка целиком).
    
3. **Регулярные выражения (Regex)**: `grep` использует регулярные выражения для описания шаблонов поиска. По умолчанию он работает с **базовыми регулярными выражениями (BRE)**, но с флагом `-E` переключается на более мощные **расширенные (ERE)**. Простые шаблоны (обычный текст) также являются регулярными выражениями, которые соответствуют сами себе.

## Флаги

### `-e` (Шаблон)

Позволяет явно указать шаблон для поиска. Это особенно полезно в двух случаях:

- Когда нужно задать **несколько шаблонов** для поиска.
- Когда шаблон **начинается с дефиса** (`-`), чтобы `grep` не принял его за флаг

**Пример:** Найти строки, содержащие «error» или «warning».
```bash
grep -e "error" -e "warning" log.txt
```

**Пример**: Найти точные вхождения **слова** `-std=c11` (флаг `-w` требует, чтобы слово совпало целиком, а не было частью другого слова):
```file
-std=c11
-std=c11345
-std
```

```bash
cat file.txt | grep -w -e "-std=c11"

-std=c11
```

#### Шаблоны с `$'\n'`

Шаблоны с реальным `\n` внутри `-e` по логике GNU это **несколько разных** шаблонов

```file.txt
apple
Apple
milk
honey
firefox
```

```bash
grep -e $'apple\nmilk' file.txt
apple
milk

grep -e 'apple\nmilk' file.txt
grep: warning: stray \ before n

grep -e $"apple\nhoney" file.txt
grep: warning: stray \ before n
```

| Команда                  | В буфере                     | Результат                    |
| ------------------------ | ---------------------------- | ---------------------------- |
| `grep -e $'milk\nhoney'` | `milk\0honey\0`              | 2 шаблона, найдёт обе строки |
| `grep -e "milk\nhoney"`  | `milk\nhoney\0` (слэш + `n`) | 1 шаблон, ничего не найдёт   |
| `grep -e milk -e honey`  | `milk\0honey\0`              | 2 шаблона, найдёт обе строки |
Сырой буфер данных `alloc_buf_t` хранит в себе строкой все найденные шаблоны, разделённые `\0`:

```bash
argv:    m i l k 0x0A h o n e y \0      (реальный перевод строки, одна C-строка)
буфер:   m i l k \0   h o n e y \0      ('\n' → '\0' в add_pattern)
```

Разделитель `\0` здесь безопасен: в `argv` его быть не может, так что он не столкнётся с содержимым шаблона. А в GNU grep разделитель `\n`, потому что там шаблоны хранятся одной строкой для `kwset` и `dfa`.

### `-i` (Игнорировать регистр)

Флаг делает поиск нечувствительным к регистру символов. Шаблон `Error` будет соответствовать и `error`, и `ERROR`, и `eRrOr`.

```file
apple
Apple
applepen other text
banana brain
app and other text
```

```bash
cat tests/data/file.txt | grep -i "apple"

apple
Apple
applepen other text
```

### `-v` (Инвертировать поиск)

Флаг меняет логику на противоположную: `grep` выводит **только те строки, которые НЕ соответствуют** шаблону. Это полезно для фильтрации нежелательных строк (например, комментариев).[](https://docs.oracle.com/cd/E36784_01/html/E36870/grep-1g.html#1)

```file.txt
apple
Apple
# comment
this is not comment
# comment 2
```

```bash
cat tests/data/file.txt | grep -v "#"

apple
Apple
this is not comment
```

### `-c` (Количество совпадающих строк)

Флаг подавляет обычный вывод и вместо этого печатает **количество строк**, которые совпали с шаблоном. Важно помнить, что считаются именно **строки**, а не отдельные вхождения. Если в одной строке слово встречается пять раз, это будет засчитано как `1`.

**Пример:** Посчитать, сколько строк в логе содержат слово `sugar`.

```file2.txt
cinnabon
sugar
coffee
milk
sugar sugar sugar
```

```bash
grep -c "sugar" tests/data/file2.txt 

2
```


### `-l` (Только имена совпадающих файлов)

Флаг подавляет вывод самих строк и вместо этого печатает **только имена файлов**, в которых было найдено хотя бы одно совпадение. Поиск в каждом файле прекращается после первого найденного совпадения для экономии времени.[](https://docs.oracle.com/cd/E36784_01/html/E36870/grep-1g.html#1)

**Пример:** Найти все `.txt` файлы в текущей директории, содержащие слово n`apple`.

```bash
grep -l "apple" tests/data/*.txt

tests/data/file1.txt
```

### `-n` (Номер строки)

Флаг добавляет к каждой выводимой строке **её порядковый номер** в файле. Это очень удобно для навигации по коду или логам

```file1.txt
apple
Apple
milk
honey
```

```file2.txt
cinnabon
sugar
coffee
milk
```

```bash
grep "milk" -n tests/data/file1.txt tests/data/file2.txt

tests/data/file1.txt:3:milk
tests/data/file2.txt:4:milk
```

### `-h` (Не выводить имена файлов)

Флаг подавляет вывод имён файлов перед совпавшими строками. Это поведение по умолчанию, если `grep` ищет только в одном файле. Однако при поиске в нескольких файлах `grep` по умолчанию добавляет имя файла к каждой строке, и `-h` отключает это, делая вывод более чистым

*(тестовые данные из примера выше)*

Без флага `-h` (обычное поведение):
```bash
grep "milk" tests/data/file1.txt tests/data/file2.txt

tests/data/file1.txt:milk
tests/data/file2.txt:milk
```

С флагом:
```bash
grep "milk" -h tests/data/file1.txt tests/data/file2.txt

milk
milk
```

### `-s` (Подавлять сообщения об ошибках)

Флаг подавляет вывод сообщений об ошибках, связанных с **несуществующими или нечитаемыми файлами**. Это может быть полезно в скриптах, где отсутствие файла — ожидаемая ситуация.[](https://docs.oracle.com/cd/E36784_01/html/E36870/grep-1g.html#1)

**Пример:** Попытаться найти «data» в файле, который может не существовать, не выводя ошибку, если его нет.

Без флага `-s` появится сообщение об ошибке:
```bash
grep "data" possibly_missing_file.txt
grep: possibly_missing_file.txt: No such file or directory
```

С флагом:
```bash
grep -s "data" possibly_missing_file.txt
```

### `-f file` (Получать шаблоны из файла)

Флаг  указывает `grep` прочитать шаблоны для поиска из указанного файла, по одному шаблону на строку. Это эквивалентно использованию нескольких флагов `-e`, но гораздо удобнее при большом количестве шаблонов.[](https://docs.oracle.com/cd/E36784_01/html/E36870/grep-1g.html#1)

**Пример:** Искать в `access.log` любые строки, содержащие IP-адреса из списка `blocked_ips.txt`.

```blocked_ips.txt
192.168.1.34
192.168.1.35
192.168.1.36
```

```access.log
192.168.1.1
192.168.1.2
192.168.1.20
192.168.1.34
192.168.1.35
192.168.1.41
```

```bash
grep -f tests/data/blocked_ips.txt tests/data/access.log

192.168.1.34
192.168.1.35
```

### `-o` (Только совпадающая часть)

Флаг выводит **только ту часть строки, которая совпала с шаблоном**, а не всю строку целиком. Каждое совпадение выводится на новой строке. Это полезно для извлечения данных (например, чисел или email-адресов) из текста.

```strings.txt
abc123def456
1000 12 madk1d 999
```

**Пример:** Извлечь все числа из строки
```bash
grep -oE "[0-9]+" tests/data/strings.txt

123
456
1000
12
1
999
```

**Пример**: Извлечь все числа, которые при этом **не являются частью других строк** (флаг `-w`)
```bash
grep -w -oE "[0-9]+" tests/data/strings.txt

1000
12
999
```

#### Особенности, применимые к `regex`

1. Флаг `REG_NOSUB` в `regcomp()` снимает с движка обязанность вычислять позиции — небольшой, но  выигрыш по производительности. Но если пользователь запустит ваш grep с `-o`, шаблон придётся перекомпилировать без этого флага. Простое решение — две ветки: с `-o` компилировать без `REG_NOSUB` и с `nmatch=1` и сдвигать поиск по строке при каждом совпадении, иначе — с `REG_NOSUB` и `nmatch=0`, чтобы не хранить информацию о позиции совпадения.
   
2. Итерация для `-o`: несколько совпадений в одной строке. `regexec` находит **одно** совпадение. Для `-o` нужно найти все в строке — цикл, сдвигая начало поиска:

```c
const char *p = line;
int first = 1;
regmatch_t m;

while (regexec(&re, p, 1, &m, first ? 0 : REG_NOTBOL) == 0) {
    int len = m.rm_eo - m.rm_so;
    if (len == 0) {            // пустое совпадение — защита от зацикливания
        if (p[m.rm_eo] == '\0') break;
        p += m.rm_eo + 1;
    } else {
        printf("%.*s\n", len, p + m.rm_so);
        p += m.rm_eo;
    }
    first = 0;
}
```

Два важных момента:
- **`REG_NOTBOL`** на всех итерациях кроме первой. Иначе `^` будет совпадать с началом **каждого**нового `p`, а не только с началом исходной строки.
- **Пустые совпадения.** Шаблон `a*` или `x?` может совпасть «вхолостую» (`rm_so == rm_eo`). Без сдвига на 1 байт — бесконечный цикл. GNU grep в `-o` пустые совпадения вообще не печатает.

#### Особенности обработки нескольких шаблонов

`grep -o` печатает совпадения в том порядке, в каком они стоят в строке. Поэтому вместо «шаблон за шаблоном» нужно двигаться по строке слева направо и на каждом шаге отвечать на вопрос: какой из шаблонов совпадает раньше всех?

```c
const char* cursor = line_buf;
while (*cursor) {
```

`cursor` указывает, с какого места мы ещё не просмотрели строку. Всё левее него уже обработано. Цикл идёт, пока строка не закончилась.

```c
int best_so = -1, best_eo = -1;
for (size_t i = 0; i < regex_list->len; i++) {
  regmatch_t pm;
  if (regexec(&regex_list->patterns[i], cursor, 1, &pm, 0) == 0) {
```

Для каждого шаблона вызываем `regexec` от текущего `cursor`. Он возвращает первое совпадение этого шаблона, где `pm.rm_so` и `pm.rm_eo` это начало и конец совпадения относительно `cursor`, а не начала строки. Это важно для арифметики ниже.

```c
if (best_so == -1 || pm.rm_so < best_so ||
    (pm.rm_so == best_so && pm.rm_eo > best_eo)) {
```

Выбираем лучшего кандидата из всех шаблонов по двум правилам:

1. Побеждает тот, у кого совпадение начинается раньше (`rm_so` меньше).
2. При равном начале побеждает более длинное (`rm_eo` больше). Так ведёт себя GNU grep: для шаблонов `app` и `apple` на слове `apple` выведет `apple`, а не `app`.

```c
if (best_so == -1) break;
```

Ни один шаблон ничего не нашёл, значит в остатке строки совпадений нет и можно выходить.

```c
if (best_eo > best_so) {
  printf("%.*s\n", best_eo - best_so, cursor + best_so);
  cursor += best_eo;
}
```

Печатаем совпадение (`%.*s` выводит ровно N символов) и переносим `cursor` на его конец. Следующий поиск начнётся уже после напечатанного, поэтому совпадения не пересекаются.

```c
else {
  cursor += best_so + 1;
}
```

Если совпадение пустое (например, шаблон `x*`), печатать нечего, но `cursor` нужно сдвинуть вперёд хотя бы на один символ. Иначе цикл никогда не закончится.

## Регулярные выражения

Любой шаблон, который вы передаете `grep`, **всегда интерпретируется как регулярное выражение** (если не указана опция `-F` или `--fixed-strings`) в режиме **BRE**.

**BRE** (Basic Regular Expressions) и **ERE** (Extended Regular Expressions) — это два режима регулярных выражений в `grep`

По умолчанию `grep` работает в режиме **BRE**:

```bash
grep "[0-9]\+" file.txt
```

Чтобы включить **ERE**, нужно указать флаг **-E**:

```bash
grep -E "[0-9]+" file.txt
```

В **GNU grep** функциональность BRE и ERE почти одинаковая. Разница только в синтаксисе: какие символы нужно экранировать обратным слэшем.

| Что нужно           | BRE (по умолчанию) | ERE (grep -E) |
| ------------------- | ------------------ | ------------- |
| Группировка         | `\(...\)`          | `(...)`       |
| Альтернатива (или)  | `\|`               | `\|           |
| Один или больше     | `\+`               | `+`           |
| Ноль или один       | `\?`               | `?`           |
| Интервал повторений | `\{n,m\}`          | `{n,m}`       |

В BRE символы `? + { } ( ) |` **по умолчанию обычные** (буквальные). Чтобы они стали метасимволами — нужно экранировать. В ERE — наоборот: они уже метасимволы, а чтобы искать их как обычные символы — нужно экранировать.

### Примеры

**Одина или больше цифр**

```Bash
# BRE
grep '[0-9]\+' file.txt

# ERE
grep -E '[0-9]+' file.txt
```

**Альтернатива** (слово "error" или "warning")

```Bash
# BRE
grep 'error\|warning' file.txt

# ERE
grep -E 'error|warning' file.txt
```

**Группировка + повторение**

```Bash
# Найти "foo", "foofoo", "foofoofoo"

# BRE
grep '\(foo\)\{2,3\}' file.txt

# ERE
grep -E '(foo){2,3}' file.txt
```

**Опциональный символ**

```Bash
# color / colour

# BRE
grep 'colou\?r' file.txt

# ERE
grep -E 'colou?r' file.txt
```

### Связь с флагом `REG_EXTENDED` в `regex`

Это прямое соответствие POSIX regex API (`regcomp` / `regexec`).

```c
#include <regex.h>

// BRE (Basic) — по умолчанию
regcomp(&re, pattern, 0);

// ERE (Extended)
regcomp(&re, pattern, REG_EXTENDED);
```

# Реализация

## Алгоритмы поиска подстроки

`grep` поддерживает 2 разных подхода поиска подстрок:
- Поиск **только одной** подстроки в файлах (`grep "apple" file.txt`, `grep "^apple" file.txt`)
- Поиск **n-подстрок** в файлах через несколько `-e` флагов или шаблон `-f`: `grep -e "apple" -e "banana" file.txt` или `grep -f keys.txt file.txt`)

Каждый из подходов, по умолчанию, интерпретирует шаблон как **регулярное выражение**, даже если шаблон состоит только из строковых литералов (`"apple"`, `"numbers"`, а не `"ap.le"` или `"numbers[0-9]\+"`)

В зависимости от подхода поиска используются соверешенно разные алгортимы

### Поиск одной подстроки

- Для большинства случаев используется алгортим **Boyer-Moore-Horspool**
- **Если нужна максимальная скорость на коротких шаблонах (до 64 символов):** лучшим выбором будет **Bitap (Shift-And)**. Он использует битовые операции и работает за O(n) с крошечной константой, но его сложнее обобщить на длинные шаблоны.

#### Алгоритм [[Boyer–Moore–Horspool#Основная идея|Боера-Мура-Хорспула]]


---
### Поиск нескольких подстрок (`-e`, `-f`)

Здесь выбор практически однозначен: **Aho-Corasick (AC)**.

- **Сложность написания:** Средняя. Нужно построить бор (trie) из всех шаблонов и добавить **failure links** (суффиксные ссылки), которые строятся BFS-обходом. Это не тривиально, но и не требует теории автоматов.
- **Скорость:** **Линейная по тексту (O(n + z))** независимо от количества шаблонов. Это его ключевое преимущество: вы проходите текст один раз, и неважно, ищете вы 10 слов или 100 000


---
### Регулярные выражения

- **PCRE2** — более мощный и функциональный вариант, но требует подключения отдельной библиотеки.
- [[regex.h#regexec()|regex]] — проще по возможностям, зато входит в стандартную библиотеку (в том числе в musl libc, который используется в Alpine Linux). Именно его мы и используем.

#### Почему нельзя обойтись фиксированным буфером

При поиске по регулярным выражениям простой overlap (перекрытие блоков) не работает. Совпадение может начинаться в одном блоке, а заканчиваться в другом (или вообще растягиваться на несколько блоков). Поэтому нам нужно гарантированно собрать **целую строку** перед тем, как отдавать её в regexec.

Для этого используется схема с двумя буферами:

| Буфер       | Тип                  | Назначение                                                                                                                                               |
| ----------- | -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `block_buf` | Фиксированный (8 КБ) | Временное хранилище сырых данных, которые возвращает `fread()`                                                                                           |
| `line_buf`  | Динамический         | Сюда собирается целая строка (даже если она пришла кусками из нескольких блоков). Расширяется до тех пор, пока не встретится `\n` или не упрёмся в лимит |

```
Файл
  │
  ▼
fread()  ──►  block_buf (сырой кусок данных)
               │
               │  memchr ищет '\n'
               ▼
          куски данных
               │
               ▼
         line_buf (собираем строку до '\n')
               │
               ▼
         готовая строка → regexec → вывод
```

#### Функция для чтения файла

Есть два основных подхода к чтению файла:

**`getline()` (POSIX)**
- Сам управляет динамическим буфером.
- Код получается очень простым:` while (getline(...) != -1)`.
- Корректно обрабатывает строки любой длины (пока хватает памяти).

**Минусы `getline()` в нашем случае:**
- Нет контроля над максимальным размером строки.
- Если на вход подать файл с гигантской строкой (или специально сформированный «злой» файл), программа может съесть всю доступную память. Это потенциальная проблема безопасности (DoS).

**Блочное чтение через `fread()`** даёт нам полный контроль:
- Мы сами решаем, до какого размера можно раздувать `line_buf`.
- При превышении лимита (`MAX_LINE_BUF_SIZE`) программа аккуратно завершается с ошибкой, а не падает из-за нехватки памяти.

#### Лимиты

```c
#define BLOCK_BUF_SIZE     8192      // 8 КБ
#define LINE_BUF_SIZE      512       // Чтобы реже делать realloc на коротких строках.
#define MAX_LINE_BUF_SIZE  (1 << 20) // 1 МБ
```

- `BLOCK_BUF_SIZE` — сколько байт за раз читаем из файла.
- `LINE_BUF_SIZE` — стартовый размер динамического буфера (чтобы на коротких строках реже делать realloc).
- `MAX_LINE_BUF_SIZE` — защита от слишком длинных строк.

#### Как работает `block_buf`

```c
char block_buf[BLOCK_BUF_SIZE];
```

Это временный буфер фиксированного размера. В него `fread()` кладёт очередной кусок файла:

```c
while ((n = fread(block_buf, sizeof(char), BLOCK_BUF_SIZE, fp)) > 0)
```

- `block_buf` - буфер для сырых данных, то куска файла длиной максимум в `BLOCK_BUF_SIZE`, он может содержать как весь файл сразу (если тот меньше, чем `BLOCK_BUF_SIZE`), как целую строку (если она ровно вместилась в размер буфера), либо, что больше всего вероятно, части нескольких строк, например:```
  apple\nApple\nmilk and banana\nhoney\nwildberries

- `sizeof(char)` - размер в байтах одного элемента, поскольку мы считываем символы, он будет равен **1**
- `BLOCK_BUF_SIZE` - количество элементов, которые нужно прочитать.
- `fp` - открытый поток 

Функция возвращает кол-во успешно прочитанных **элементов**, и если оно больше нуля, мы обрабатываем полученные данные.

В одном блоке могут оказаться:
- несколько целых строк;
- кусок строки + несколько целых строк + начало следующей строки;
- просто середина очень длинной строки.

После чтения мы работаем с двумя указателями:

```c
char* curr = block_buf;   // начало ещё не обработанных данных
char* end  = block_buf + n; // первый байт после конца прочитанных данных
```

Внутренний цикл с помощью `memchr()` ищет ближайший `\n`. Как только находит — копирует кусок в `line_buf`, добавляет завершающий `\0` и отдаёт строку в `regexec`. После этого `curr` сдвигается сразу за найденный `\n`, и процесс повторяется.

Если `\n` в текущем блоке не найден — весь оставшийся кусок дописывается в `line_buf`, и мы идём читать следующий блок.

В самом конце (после цикла `fread()`) отдельно обрабатывается «хвост» — последняя строка файла, если она не заканчивается переводом строки.

#### Внутренний цикл: как мы вытаскиваем строки из блока

После того как `fread()` положил данные в `block_buf`, мы получаем два указателя: `curr` будет двигаться вперёд по мере того, как мы находим и обрабатываем строки. `end` остаётся неподвижным — он показывает границу текущего блока.

Внутри цикла мы постоянно ищем ближайший символ перевода строки:

```c
char* nl = memchr(curr, '\n', end - curr);
```

`memchr()` ищет байт `\n` в первых `end - curr` байтах той области памяти, на которую указывает `curr` . Это очень быстрая операция.

> Арифметика указателей `end - curr` возвращает `size_t` тип данных, описывающий кол-во элементов между `curr` и `end` ячейками данных. Например, `curr` равно адресу в памяти **1012**, `end` указывает на **1112** ячейку, значит кол-во элементов между ними **100**

Дальше вычисляем длину текущего куска:

```c
size_t chunk_len = nl ? (nl - curr) : (end - curr);
```

- Если `\n` нашёлся — `chunk_len` равен расстоянию от текущего положения до этого `\n` (сам `\n` в кусок **не** входит).
- Если `\n` не нашёлся — берём всё, что осталось до конца блока, и читаем новый блок сырых данных через `fread()`

#### Что такое `line_buf`

В `line_buf` должна хранится одна целая строка. При этом нам неважно, попала ли она туда за одно чтение блока сырых данных `block_buf` или пришлось делать несколько раз вызов `fread()` и склеивать между собой блоки данных между вызовами.

В начале программы буфер строки выглядит так:

```c
char* line_buf = NULL;   // указатель никуда не указывает
size_t line_cap = 0;     // текущая вместимость = 0 байт
size_t line_len = 0;     // сколько байт уже занято = 0
```

То есть памяти под строку ещё **нет вообще**. Это нормально и даже желательно: зачем выделять память заранее, если файл может быть пустым или состоять из очень коротких строк.

#### `ensure_capacity()` расширение памяти под буфер `line_buf`

**Когда впервые появляется потребность в памяти** — представим, что `fread()` прочитал первый блок и мы нашли кусок данных длиной `chunk_len`. Сейчас неважно, есть ли в этом куске данных `\n` или нет.

Перед копированием вызывается:

```c
ensure_capacity(&line_buf, &line_cap, chunk_len + line_len + 1);
```

Поскольку сейчас `line_len == 0`, мы просим место под `chunk_len` + 1 байт (сам кусок + завершающий `\0`).

**Как работает ensure_capacity при первом выделении**. Разберём функцию по шагам:

```c
int ensure_capacity(char** line_buf, size_t* cap, size_t needed) {
    if (needed <= *cap) return 0;   // места уже хватает — ничего не делаем
```

На первом вызове `*cap == 0`, а `needed > 0`, поэтому условие не срабатывает и мы идём дальше:

```c
size_t new_cap = *cap ? *cap * 2 : LINE_BUF_SIZE;
```

Поскольку `*cap == 0`, берётся стартовое значение `LINE_BUF_SIZE` (**512** байт).

```c
while (new_cap < needed) new_cap *= 2;
```

Если **512 байт** всё ещё мало (например, первый кусок оказался очень большим), ёмкость продолжает удваиваться, пока не станет достаточной.

```c
if (new_cap <= MAX_LINE_BUF_SIZE) {
        char* tmp = realloc(*line_buf, new_cap);
```

`realloc(NULL, new_cap)` ведёт себя точно так же, как `malloc(new_cap)`. То есть при первом вызове происходит обычное выделение памяти. Если `realloc` успешен:

```c
*cap = new_cap;       // запоминаем новую вместимость
        *line_buf = tmp;      // теперь line_buf указывает на выделенную память
```

Если `realloc` вернул `NULL` или мы превысили `MAX_LINE_BUF_SIZE` — возвращается ошибка `-1`.

**Копирование данных в буфер**. После успешного `ensure_capacity()` выполняется:

```c
memcpy(line_buf + line_len, curr, chunk_len);
line_len += chunk_len;
```

Разберём, что происходит:
- `line_buf + line_len` — адрес, начиная с которого можно безопасно писать.  
    На первом копировании `line_len == 0`, поэтому пишем прямо в начало буфера.
- `curr` — откуда берём данные (из `block_buf`).
- `chunk_len` — сколько байт копируем.

После `memcpy()` длина занятой части увеличивается:

```
line_len += chunk_len;
```

Теперь `line_len` показывает, сколько полезных байт уже лежит в буфере (без учёта завершающего нуля). 

> Завершающий нуль добавляется для формирования корректной C-строки, как раз такой, какую от нас ждём `regexec()`

#### Что происходит, когда строка ещё не закончилась

Если в текущем блоке `\n` не найден, внутренний цикл просто завершается (`break`).  
При этом:

- `line_buf` продолжает существовать;
- `line_len` хранит, сколько байт уже накоплено;
- `line_cap` хранит текущую вместимость.

При следующем вызове `fread()` мы снова зайдём в `ensure_capacity()`. Теперь `line_len` уже не ноль, поэтому запрашиваемый размер будет:

```c
needed = chunk_len + line_len + 1;
```

Если места хватает — просто дописываем новый кусок в конец:

```c
memcpy(line_buf + line_len, curr, chunk_len);  // пишем ПОСЛЕ уже имеющихся данных
line_len += chunk_len;
```

Если места не хватает — `ensure_capacity` увеличит буфер (в 2 раза), скопирует старые данные в новое место (это делает сам `realloc`), и только после этого произойдёт `memcpy`, чтобы скопировать в `line_buf` новые данные к уже имеющимся там после предыдущих вызовов `fread()`.

#### Что происходит, когда строка завершилась (`\n` найден)

```c
line_buf[line_len] = '\0';     // ставим завершающий ноль
reti = match(&regex, line_buf); // теперь это полноценная C-строка

if (reti == 0) {
    printf("%s\n", line_buf);
}

// Важно: память не освобождаем!

line_len = 0;  // просто говорим, что буфер снова пуст
curr = nl + 1; // curr теперь указывает на следующий символ после \n
```

Обратите внимание: мы **не** делаем `free()` и **не** обнуляем `line_buf`.  Мы лишь сбрасываем `line_len` в ноль. Это позволяет переиспользовать уже выделенную память для следующих строк и не делать лишних манипуляций. Следующая строка начнёт записываться с начала того же буфера.

#### Повторное использование буфера

Предположим, первая строка была длинной (буфер вырос, например, до **4096 байт**).  
Следующая строка оказалась короткой (**20 байт**).

При обработке второй строки:

```c
ensure_capacity(..., 20 + 0 + 1);
```

Поскольку `needed (21) <= line_cap (4096)`, функция сразу возвращает **0** и ничего не делает. Мы просто перезаписываем начало буфера новыми данными. Старые данные «забываются», потому что `line_len` снова станет маленьким.

Это очень эффективный подход: мы платим за выделение памяти только когда строка действительно становится длиннее предыдущих.

#### Обработка самой последней строки файла

После того как `fread()` больше ничего не возвращает, может остаться «хвост» — последняя строка, которая не заканчивалась `\n`.

```c
if (line_len > 0 && !is_error) {
    line_buf[line_len] = '\0';
    // ... проверка регулярки и вывод
}
```

Здесь `line_len` уже содержит правильную длину накопленных данных, поэтому нам достаточно только поставить `\0` и обработать строку.

#### Освобождение памяти

В самом конце программы:

```
free(line_buf);
```

Даже если `line_buf` так и остался `NULL` (файл был пустым), `free(NULL)` безопасен и ничего не сделает.

#### Краевые случаи 

| Ситуация                                       | Как обрабатывается                                                                 |
| ---------------------------------------------- | ---------------------------------------------------------------------------------- |
| Пустая строка (`\n\n`)                         | `chunk_len == 0`, в `line_buf` кладётся только `\0`, регулярка проверяется         |
| Файл без завершающего `\n`                     | Обрабатывается в финальном блоке после цикла                                       |
| Очень длинная строка (больше `BLOCK_BUF_SIZE`) | Собирается по частям в `line_buf` через несколько вызовов `fread()`                |
| Строка длиннее `MAX_LINE_BUF_SIZE`             | `ensure_capacity()` возвращает ошибку, программа завершается                       |
| Файл меньше одного блока                       | Всё обрабатывается за один проход                                                  |
| Строка целиком лежит внутри одного блока       | Копируется и сразу проверяется                                                     |
| Строка разбита между двумя блоками             | Первая часть сохраняется в `line_buf`, вторая дописывается при следующем `fread()` |

### Оптимизация выбора алгоритма

GNU `grep` оптимизирует даже `regex`:

1. Даже если паттерн — регулярка, он пытается вытащить из неё **фиксированную подстроку** (literal), которую обязана содержать любая подходящая строка.
2. По этой фиксированной подстроке гоняет быстрый `Boyer-Moore` по всему файлу.
3. Только когда находит кандидата — запускает полноценный regex-матчер на этой строке.

Поэтому даже обычный `grep 'error'` часто почти так же быстр, как `grep -F 'error'`

Процесс состоит из двух основных этапов: **извлечение литерала** из регулярного выражения и **построение префильтра**.

#### Этап 1: Разбор регулярного выражения и извлечение литерала

Вам нужно проанализировать шаблон регулярного выражения, чтобы найти в нём самую длинную непрерывную последовательность обычных символов (не метасимволов).

- **Что считать «обязательным»:** Литерал обязателен, если он находится в **основной конкатенации** регулярного выражения. Например, в `foo.*bar` обязательными являются и `foo`, и `bar`, но `bar` длиннее, поэтому его выгоднее использовать для фильтрации.

- **Что не является обязательным:** Символы внутри альтернации `(foo|bar)` не обязательны (строка может содержать `foo`, а может `bar`), поэтому их нельзя использовать как единый обязательный литерал. Символы внутри квантификаторов `(foo)*` или `(foo)+` также не обязательны, так как группа может встретиться ноль раз.

**Практический подход для вашей реализации:**

1. **Постройте простое абстрактное синтаксическое дерево (AST)** для вашего регулярного выражения. Вам не нужен полноценный парсер, достаточно простого рекурсивного анализатора.
2. **Обходите дерево**, отслеживая «текущий литеральный буфер» — последовательность обычных символов.
3. Когда вы встречаете метасимвол (например, `.`, `*`, `[`, `(`), «сбрасывайте» текущий буфер. Если его длина больше, чем у ранее найденного лучшего литерала, запоминайте его.
4. **Пропускайте** ветви дерева, соответствующие альтернации и квантификаторам, так как их содержимое не является обязательным.

В результате вы получите строку, которая **гарантированно** должна быть в любой подходящей строке, или `NULL`, если такого литерала нет (например, для шаблона `.*`).

#### Этап 2: Построение префильтра и его интеграция

Когда у вас есть обязательный литерал, вы можете построить для него быстрый поисковый механизм. В терминах GNU grep этот механизм называется **kwset** (keyword set).

**Архитектура вашего `s21_grep` с префильтром:**

1. **Компиляция:** При старте программы, после разбора аргументов, для каждого регулярного выражения:

    - Вызовите вашу функцию извлечения литерала.
    - Если литерал найден, скомпилируйте для него **Boyer-Moore** (или Aho-Corasick, если у вас несколько шаблонов). Сохраните этот «префильтр» вместе с скомпилированным регулярным выражением.
        
2. **Процесс поиска:** Для каждой строки входного файла:
    
    - **Шаг A (Быстрый фильтр):** Запустите ваш префильтр (Boyer-Moore) для поиска обязательного литерала в строке.
        
    - **Шаг B (Проверка):**
        
        - Если литерал **не найден**, вы можете со **100% уверенностью** сказать, что строка не соответствует регулярному выражению, и перейти к следующей строке, **не вызывая**медленный regex-матчер. Это и есть основная экономия времени.
        - Если литерал **найден**, только тогда вызывайте полноценный `regexec()` (или вашу функцию regex-поиска) для этой строки, чтобы получить точный результат.
            

#### Итог: что это даст и когда не сработает

- **Выигрыш:** На больших объемах данных, где большинство строк не соответствуют шаблону, такая схема может дать **многократное ускорение**. Время будет тратиться в основном на очень быстрый поиск подстроки, а не на медленный regex-движок.
    
- **Ограничения:** Оптимизация **не поможет** (или поможет слабо), если:
    
    - В регулярном выражении **нет обязательного литерала** (например, шаблон `.*` или `[a-z]+`).
    - Обязательный литерал **очень короткий** (1-2 символа). В этом случае фильтр будет пропускать слишком много строк, и выигрыш будет незначительным.

## Сборка нескольких шаблонов

При разборе аргументов в `parse_args()` компилировать шаблоны сразу в `regex_t` нельзя, так как даже отказ от `-E` проблему не снимает: `regcomp` зависит не только от `-E`, но и от **`-i`** (`REG_ICASE`), а `-o` определяет, можно ли ставить `REG_NOSUB`. Порядок опций в командной строке произвольный, поэтому в `grep -e abc -i file` на момент разбора `-e` вы ещё не знаете, что нужен `REG_ICASE`. Если скомпилировать сразу, `-i` после `-e` молча не сработает.

Компилировать нужно один раз, после разбора всех аргументов и до чтения файлов. В `case 'e'` это делать нельзя, так как флаги `regcomp` должны быть известны заранее.

**Два формата данных:**
1. **Сырые шаблоны** (`alloc_buf_t`, `pat1\0pat2\0`). Это транспорт между `parse_args` и компиляцией, ничего больше.
2. **Скомпилированные** (массив `regex_t` с количеством). С ними работает матчинг.

```c
// types.h
typedef struct {
  regex_t* items;
  size_t count;  // сколько элементов реально скомпилировано
} regex_list_t;
```



```c
static size_t count_patterns(const alloc_buf_t* src) {
  size_t count = 0;
  const char* end = src->data + src->len;

  for (const char* p = src->data; p < end; p += strlen(p) + 1) count++;

  return count;
}

static int compile_one(const char* pattern, int cflags, regex_t* re) {
  int rc = regcomp(re, pattern, cflags);

  if (rc != 0) {
    char msg[256];
    regerror(rc, re, msg, sizeof msg);
    fprintf(stderr, "s21_grep: %s: %s\n", pattern, msg);
  }

  return rc == 0 ? 0 : -1;
}

void free_regex_list(regex_list_t* list) {
  for (size_t i = 0; i < list->count; i++) regfree(&list->items[i]);
  free(list->items);
  list->items = NULL;
  list->count = 0;
}

int compile_patterns(const alloc_buf_t* src, int cflags, regex_list_t* out) {
  int status = 0;
  size_t total = count_patterns(src);

  out->count = 0;
  
  // Поскольку нам заранее известно число шаблонов из сырых данных,
  // мы можем сразу под них всех выделить память
  out->items = calloc(total, sizeof(regex_t));
  if (total > 0 && out->items == NULL) status = -1;

  const char* p = src->data;
  const char* end = src->data + src->len;

  while (status == 0 && p < end) {
    status = compile_one(p, cflags, &out->items[out->count]);
    if (status == 0) out->count++;
    p += strlen(p) + 1;
  }

  if (status != 0) free_regex_list(out);

  return status;
}

int main(int argc, char* argv[]) {
  int status = 0;
  opts_t opts = {0};
  
  // Буфер под сырые данные шаблонов
  alloc_buf_t raw = {0};
  
  // Буфер под скомпилированные шаблоны
  regex_list_t regs = {0};

  status = parse_args(argc, argv, &opts, &raw);
  if (status == 0) status = compile_patterns(&raw, make_cflags(&opts), &regs);
  free(raw.data);  // после компиляции сырые шаблоны не нужны
  if (status == 0) status = process_files(argc, argv, &opts, &regs);
  free_regex_list(&regs);  // безопасно и для нулевой структуры

  return status == 0 ? EXIT_SUCCESS : EXIT_FAILURE;
}
```

- `count` растёт только после успешного `regcomp`. Поэтому при ошибке на третьем шаблоне `free_regex_list` освободит ровно два. Для неудавшегося `regcomp` вызывать `regfree` не нужно.
- `regex_t` не хранит ссылку на строку шаблона (в glibc и musl). Значит, сырой буфер можно освобождать сразу после компиляции.

### Зачем `regfree` для каждого, если есть `free(items)`

`free(items)` освобождает только **ту память, которую вы выделили сами**: сам массив структур `regex_t`. Но каждый `regex_t` после успешного `regcomp` внутри держит **собственные указатели на память, которую выделил сам `regcomp`** (скомпилированный автомат, таблицы и т. п.). `free(items)` про эту память ничего не знает, она останется в утечке.

```
items ──► [ regex_t #0 ][ regex_t #1 ]      ← это освобождает free(items)
               │              │
               ▼              ▼
        внутренний буфер  внутренний буфер  ← это освобождает только regfree
        (выделил regcomp) (выделил regcomp)
```

Порядок важен: сначала `regfree` для каждого элемента (пока массив жив), потом `free(items)`. Если сделать наоборот, `regfree` получит указатели на уже освобождённую память.

## Как цикл понимает границы элементов

Он их не ищет, а **вычисляет**. `items` имеет тип `regex_t*`, поэтому компилятор знает `sizeof(regex_t)` и `items[i]` превращает в сдвиг на `i * sizeof(regex_t)` байт от начала:

```c
items[i]   ≡   *(items + i)   // items + i сдвигает адрес на i * sizeof(regex_t)
&items[i]  ≡   items + i
```

Границы задаются тем, что вы при `calloc(total, sizeof(regex_t))` выделили место ровно под `total` структур, а `count` говорит, сколько из них реально инициализировано. Выходить за `count` нельзя, поэтому цикл `i < count`.

## Пример: как выглядит `items`

Команда: `s21_grep -e abc -e 'num[0-9]' -i file.txt`

После разбора аргументов сырой буфер:

```
raw.data = "abc\0num[0-9]\0"      raw.len = 13
```

Компиляция:

```c
regex_list_t regs = {0};
// count_patterns(&raw) == 2
regs.items = calloc(2, sizeof(regex_t));
regs.count = 0;

compile_one("abc",       REG_ICASE, &regs.items[0]);  regs.count = 1;
compile_one("num[0-9]",  REG_ICASE, &regs.items[1]);  regs.count = 2;
```

Состояние в памяти:

```
regs.items ──► ┌─────────────────────────┐
               │ items[0]: regex_t       │  ← скомпилированный "abc"
               │   re_nsub = 0           │
               │   (внутри указатель     │
               │    на данные regcomp)   │
               ├─────────────────────────┤
               │ items[1]: regex_t       │  ← скомпилированный "num[0-9]"
               │   re_nsub = 0           │
               │   (внутри указатель...) │
               └─────────────────────────┘
regs.count = 2
```

Использование:

```c
// строка "Apple num5"
regexec(&regs.items[0], "Apple num5", 0, NULL, 0);  // REG_NOMATCH ("abc" нет)
regexec(&regs.items[1], "Apple num5", 0, NULL, 0);  // 0 (совпало "num5")
```

Освобождение:

```c
for (size_t i = 0; i < regs.count; i++) regfree(&regs.items[i]);  // внутренняя память regcomp
free(regs.items);                                                  // массив структур
```

Обратите внимание, что содержимое `regex_t` (поля внутри) определяет реализация libc, и обращаться к нему напрямую не нужно. Для вас `regex_t` это непрозрачный объект, который работает только в паре `regcomp` → `regexec` → `regfree`.
