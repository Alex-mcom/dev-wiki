
## 1. Владение ресурсами

**Правило: кто выделил, тот и освободил, причём на том же уровне абстракции.**

- Ресурс = память, `FILE*`, дескриптор. У каждого ресурса один владелец, остальные функции только «одалживают» его по указателю и не освобождают.
- Если ресурс живёт дольше одной функции, делайте пару `init` / `destroy`. Владелец вызывает `init` в начале и `destroy` в конце, всё между ними работает с указателем.
- Инициализируйте всё нулями (`pattern_t p = {0}`). Тогда `destroy` безопасен в любом состоянии, в том числе после неудачного `init`, потому что `free(NULL)` ничего не делает.
- **Если функция упала посреди работы, она сама убирает то, что успела выделить внутри себя**, и оставляет объект в состоянии, которое можно передать в `destroy`. Вызывающий не знает, что именно было выделено.
- Исключение из «освобождает владелец» только одно: функция-фабрика (`create_x`), которая явно возвращает новый ресурс. Тогда владение передаётся вызывающему, и это нужно написать в комментарии.

## 2. Обработка ошибок: хватит ли `is_error`?

Для ваших задач хватит. Три уровня, от простого к серьёзному:

|Уровень|Когда|Как|
|---|---|---|
|Флаг 0/1|Достаточно знать «успех или нет», сообщение уже выведено|`int is_error`|
|`enum` кодов|Нужно различать причины (память, аргументы, ввод-вывод) или решать, что делать дальше|`ERR_OK = 0, ERR_MEM, ERR_ARG, ERR_IO`|
|Структура ошибки (код + текст + контекст)|Библиотеки, сложные программы|В школьных проектах избыточно|

Рекомендую сразу заводить `enum`: он ничего не усложняет, а код читается лучше, чем «магическая» единица.

```c
typedef enum { ERR_OK = 0, ERR_ARG, ERR_MEM, ERR_IO } err_t;
```

**Пробрасывание без вложенных `if`:**

```c
err_t err = init_pattern(&p);
if (err == ERR_OK) err = parse_args(argc, argv, &opts, &p);
if (err == ERR_OK) err = run(&opts, &p);
cleanup(&p);
return err;
```

Каждый шаг выполняется, только если предыдущие прошли. Вложенность не растёт, `goto` не нужен.

**Кто печатает сообщение:** либо место, где ошибка возникла (один раз, не дублировать на каждом уровне), либо `main` по коду. Не печатайте и там, и там.

## 3. Можно ли `exit(1)` в функциях выделения памяти?

Технически с точки зрения C это легально, и в реальных утилитах часто делают обёртку `xmalloc` с `exit`, когда нехватка памяти фатальна. Но в вашем контексте я бы не стал, по причинам:

- Это второй выход из программы, что нарушает принцип одного выхода (следствие 2). Проверяющий вправе придраться.
- Для `clean()` перед `exit` понадобились бы глобальные переменные или указатель на всё состояние, которое тянется через все функции.
- Функция перестаёт быть переиспользуемой, потому что решает судьбу всей программы за вызывающего.

`valgrind` на `exit()` с неосвобождёнными блоками обычно ругается как на «still reachable», а не «definitely lost». Но проверка памяти у вас, скорее всего, строгая, так что лучше освобождать всё честно.

Ответ на вопрос «зачем пробрасывать, если обработать нечем»: наверху не обрабатывают, а **доводят управление до владельца, чтобы тот освободил ресурсы и завершился штатно**. Это и есть вся «обработка» фатальной ошибки.

## 4. Какие коды возвращать

Общепринятое соглашение C:

- **Функции действия** (`init`, `parse`, `add`): `0` успех, **ненулевое значение** ошибка. Это обратно булевой логике, зато так делают стандартная библиотека и POSIX.
- **Предикаты** (`is_empty`, `has_flag`): `1` истина, `0` ложь. Называйте их через `is_` / `has_`, тогда путаницы с предыдущим пунктом не будет.
- **Функции, возвращающие указатель:** `NULL` при ошибке.
- **Функции, которым нужно вернуть и значение, и статус:** результат через выходной параметр (`size_t* out`), статус через `return`.
- Не смешивайте `-1` и `1` для ошибки в одном проекте. Выберите один стиль.

**Что возвращает `main`:** только через единственный `return` в конце. Используйте `EXIT_SUCCESS` (0) и `EXIT_FAILURE` из `<stdlib.h>`, либо ваш `enum`, если код ошибки значим. Эффективно доступны значения 0–255.

Если вы делаете клон `grep`, у настоящего `grep` свои коды: 0 нашли совпадение, 1 не нашли, 2 ошибка. Проверьте, что требует ваше задание, возможно, там важен только ноль/не ноль.

## 5. Глобальные переменные

**Нет, даже если очень хочется.** Правило школы прямое, и обойти его не получится.

Желание завести глобальную переменную почти всегда означает, что нужна **структура контекста**, которую вы передаёте по указателю:

```c
typedef struct {
  opts_t opts;
  pattern_t pattern;
} app_t;
```

- `static`-переменные внутри функций тоже скрытое глобальное состояние, лучше их избегать.
- Константы делайте через `#define` или `enum`, а не `const int` на уровне файла.
- Глобальные `optarg` и `optind` из `getopt` — это libc, их использовать можно, вы их не объявляете.

## 6. Шаблон функции под все правила

```c
err_t do_something(ctx_t* ctx, const char* input) {
  err_t err = ERR_OK;
  char* buf = NULL;

  if (ctx == NULL || input == NULL) return ERR_ARG;  // единственный ранний выход

  buf = malloc(SIZE);
  if (buf == NULL) err = ERR_MEM;

  if (err == ERR_OK) err = step_one(ctx, buf);
  if (err == ERR_OK) err = step_two(ctx, buf);

  free(buf);  // владелец освобождает всегда, при любом исходе
  return err;
}
```

Заодно по циклам: условие продолжения (`!is_error && ...`) заменяет `break`, а если выходов из цикла нужно несколько, выносите тело в функцию.
