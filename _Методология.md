## `static` для функций

**Главное правило:** если функции нет в `.h`, она `static`. Если она в `.h`, то не `static`. Заголовок описывает публичный интерфейс файла, всё остальное приватное.

### Общие правила

- **Прототипы**: Прототипы `static` функций **всегда наверху**. Они служат оглавлением файла: по ним видно, из чего состоит программа, не читая тел. Для не `static`-функций следует выносить прототипы в `.h`

### Файл-модуль (`foo.c` + `foo.h`)

- **Без `static`:** функции, объявленные в `foo.h`, то есть то, что вызывают другие файлы.
- **`static`:** все вспомогательные функции, которые нужны только внутри `foo.c`: разбор, проверки, куски, на которые разбита большая публичная функция.
- **Проверка:** если функцию хочется вызвать из другого файла, сначала подумайте, не ошибка ли это в разбиении на модули. Если нет, добавьте её в `.h` и уберите `static`.

### Файл с точкой входа (`main.c`)

- **Без `static`:** только `main`, он всегда внешний.
- **`static`:** абсолютно всё остальное. Заголовка у `main.c` обычно нет, значит, публичного интерфейса нет, поэтому прототипы только в `.c`, не в `.h`.
- **Исключение:** если из `main.c` вынесли функцию, которой пользуются другие файлы, ей место в модуле, а не в `main.c`.

### Что даёт `static`

- **Конфликты имён.** Если в другом файле появится функция с таким же именем, например `PrintUsage` в будущем модуле, линкер выдаст ошибку. С `static` каждый файл имеет собственную копию имени. То же с libc: функцию вроде `ProcessFile` легко случайно назвать как чужую.
- **Предупреждения.** Для `static`-функции, которую никто не вызывает, `-Wall` выдаст `-Wunused-function`. Для обычной функции предупреждения не будет, и мёртвый код останется незамеченным. Для вашего проекта это самый ощутимый плюс.
- **Оптимизация.** Компилятор знает, что все вызовы видны, и может встроить функцию или вовсе убрать.
- **Читаемость.** Видно, что функция внутренняя и её можно менять, не думая о других файлах. Публичный интерфейс файла виден как набор функций без `static`, и он совпадает с заголовком.

## Разработка сверху вниз (`top-down`)

Сначала пишете самый верхний уровень: что программа делает в целом, в виде последовательности вызовов. Каждый вызов это функция следующего уровня, которую вы раскрываете позже. Каждая функция работает на одном уровне детализации: её имя говорит «что», а тело состоит из вызовов «как» на уровень ниже.

>- **Top-down:** `main` первым, прототипы наверху, определения сверху вниз.
>- **Bottom-up:** функции определены до использования, прототипов нет, `main` в самом конце.

### Порядок работы

1. Напишите `main` как последовательность вызовов: разобрать аргументы, подготовить данные, обработать, вывести результат, освободить ресурсы.
2. Для каждого вызова напишите прототип и заглушку, которая возвращает фиктивное значение. Программа должна компилироваться на каждом шаге.
3. Раскрывайте заглушки по одной, по тому же принципу. Если внутри нужен кусок логики, выносите его в функцию следующего уровня.
4. Собирайте с `-Wall -Wextra -Werror` и проверяйте после каждого шага.

### Когда выделять функцию

- Тело длиннее 40–50 строк.
- Вложенность блоков больше 4.
- Блок приходится объяснять комментарием: комментарий превращается в имя функции.
- Фрагмент повторяется.

### Расположение в файле

Сверху вниз, как в оглавлении:

```
1. #include (системные, затем свои)
2. #define и константы
3. типы, нужные только этому файлу
4. прототипы static-функций, в порядке вызова
5. main
6. определения функций в том же порядке, что и прототипы
```

- **Прототипы всегда наверху.** Они служат оглавлением файла: по ним видно, из чего состоит программа, не читая тел.
- **Порядок определений совпадает с порядком прототипов.** Тогда читать файл можно линейно: сначала `main`, потом то, что он вызывает, потом то, что вызывают те функции.
- **Прототип `static`-функции пишется со `static`.** В определении `static` лучше повторить, чтобы при чтении тела было видно видимость функции.
- **Прототипы приватных функций остаются в `.c`.** В `.h` попадают только публичные.

### Если файл это модуль

- В `.h` публичные прототипы в том же порядке сверху вниз: от главных функций модуля к вспомогательным.
- В `.c` под `#include` идут прототипы `static`-функций, затем определения. Точки входа в модуль нет, поэтому порядок задают публичные функции: сначала они, потом их внутренние помощники.
