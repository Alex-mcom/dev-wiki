## Что такое GCC

**GCC (GNU Compiler Collection)** — набор компиляторов проекта GNU. Раньше расшифровывался как _GNU C Compiler_, но теперь умеет не только C: C++, Objective-C, Fortran, Ada, Go, D. Для каждого языка есть свой _front end_ (разбор исходника), а общая часть (_middle end_ и _back end_) оптимизирует код и генерирует машинные инструкции под нужную архитектуру (x86-64, ARM, RISC-V и т. д.).

### Команда `gcc` — это драйвер

Когда вы пишете `gcc main.c`, сам `gcc` почти ничего не компилирует. Это **программа-драйвер**: она смотрит на расширения файлов и флаги, а затем по очереди запускает нужные утилиты:

| Этап                                   | Кто выполняет                                | Что запускает драйвер                 |
| -------------------------------------- | -------------------------------------------- | ------------------------------------- |
| Препроцессинг и компиляция в ассемблер | `cc1` (собственно компилятор)                | внутренний исполняемый файл GCC       |
| Ассемблирование                        | `as` (из binutils)                           | превращает `.s` в `.o`                |
| Линковка                               | `ld` (из binutils), через обёртку `collect2` | собирает `.o` и библиотеки в бинарник |

Увидеть все эти вызовы можно флагом `-v` (или `-###`, который только печатает команды, не выполняя их).

### GCC и toolchain

GCC — центральная часть **toolchain** (цепочки инструментов для сборки). Помимо него в сборке участвуют:

- **binutils** — `as` (ассемблер), `ld` (линковщик), `ar` (архиватор для `.a`), `ranlib`, `nm` (список символов), `objdump` (дизассемблер и разбор объектных файлов), `strip`, `readelf`;
- **стандартная библиотека C** (в Linux обычно glibc) и её заголовки (`stdio.h`, `string.h` …);
- **служебные объекты запуска** (`crt1.o`, `crti.o`, `crtn.o`) — код, который выполняется до `main` и после него;
- **libgcc** — вспомогательные функции компилятора (например, арифметика, которую процессор не умеет выполнять одной командой).

> На macOS команда `gcc` — обычно алиас на Clang. Всё ниже верно и для него в части флагов, но `ld` там другой (Apple ld), а динамические библиотеки имеют расширение `.dylib`.

### Самые частые флаги

| Флаг                    | Что делает                                                         |
| ----------------------- | ------------------------------------------------------------------ |
| `-o <файл>`             | задаёт **имя выходного файла**                                     |
| `-c`                    | только компиляция до `.o`, без линковки                            |
| `-E`                    | только препроцессор, результат — в stdout                          |
| `-S`                    | остановиться после генерации ассемблера (`.s`)                     |
| `-I<dir>`               | где искать заголовочные файлы                                      |
| `-L<dir>`               | где искать библиотеки при линковке                                 |
| `-l<имя>`               | подключить библиотеку `lib<имя>.a` / `lib<имя>.so`                 |
| `-D<MACRO>[=val]`       | определить макрос из командной строки                              |
| `-g`                    | добавить отладочную информацию (для gdb)                           |
| `-O0` … `-O3`, `-Os`    | уровень оптимизации (`-O0` — без оптимизаций, по умолчанию)        |
| `-Wall -Wextra -Werror` | включить предупреждения и считать их ошибками                      |
| `-v`                    | показать, какие программы и с какими аргументами запускает драйвер |


```bash
gcc -Wall -Wextra -Werror -std=c11 main.c -o app
```

## Этапы сборки

Из `.c`-файла до исполняемого файла код проходит **четыре этапа**. Каждый .c-файл при этом обрабатывается **независимо от остальных** — поэтому компилятор «не знает» про функции из других файлов, пока вы не объявите их в заголовках (прототипы в `.h`).

| №   | Этап            | Программа            | Вход                  | Выход                     | Остановиться после него |
| --- | --------------- | -------------------- | --------------------- | ------------------------- | ----------------------- |
| 1   | Препроцессинг   | `cpp` (внутри `cc1`) | `main.c`              | `main.i`                  | `gcc -E`                |
| 2   | Компиляция      | `cc1`                | `main.i`              | `main.s` (ассемблер)      | `gcc -S`                |
| 3   | Ассемблирование | `as`                 | `main.s`              | `main.o` (объектный файл) | `gcc -c`                |
| 4   | Линковка        | `ld`                 | `main.o` + библиотеки | исполняемый файл          | — (без `-c/-S/-E`)      |

```bash
gcc -E main.c -o main.i   # 1. препроцессинг
gcc -S main.i -o main.s   # 2. компиляция в ассемблер
gcc -c main.s -o main.o   # 3. ассемблирование в объектный файл
gcc main.o -o app         # 4. линковка в исполняемый файл
```

Обычно же пишут `gcc -c main.c` (этапы 1–3 разом) и `gcc main.o -o app` (этап 4). Драйвер определяет, что делать, **по расширению файла**: `.c` — исходник C, `.i` — уже препроцессированный, `.s` — ассемблер, `.S` — ассемблер с препроцессором, `.o` — объектный файл, `.a` / `.so` — библиотеки.

### 1. Препроцессинг (`-E`)

Чисто **текстовая** обработка, о синтаксисе C препроцессор ничего не знает:

- `#include` — подставляет содержимое заголовка прямо в текст;
- `#define` — выполняет подстановку макросов;
- `#if`, `#ifdef`, `#ifndef` — вырезает ненужные ветки кода;
- удаляет комментарии и склеивает строки с `\`.

Результат называется **единицей трансляции** (_translation unit_) — один большой файл без директив `#`, который и увидит компилятор.

### 2. Компиляция (`-S`)

Компилятор проверяет и переводит код:

- **лексический разбор** — текст превращается в токены;
- **синтаксический разбор** — строится дерево программы, проверяется грамматика;
- **семантический анализ** — типы, объявления, количество аргументов;
- **оптимизации** (зависят от `-O`) на промежуточных представлениях;
- **генерация ассемблера** под конкретную архитектуру.

Именно здесь появляются ошибки вида `expected ';'` и предупреждения (`-Wall`, `-Wextra`).

### 3. Ассемблирование (-`c`)

`as` превращает текст ассемблера в **машинный код** и упаковывает его в **объектный файл** (на Linux — формат ELF _relocatable_). Это ещё не программа: адреса функций и данных не окончательные, а вызовы чужих функций (например, `printf`) помечены как «разрешить потом».

**`-c` означает «compile only»**: выполнить препроцессинг, компиляцию и ассемблирование, но **не запускать линковщик**. На выходе — объектный файл `.o` для каждого переданного `.c`. Если `-o` не указан, имя образуется заменой расширения: `main.c` → `main.o` (в текущем каталоге).

```bash
gcc -c main.c            # получится main.o
gcc -c add.c mul.c       # получится add.o и mul.o
gcc -c main.c -o obj/m.o # результат под другим именем и в другом каталоге
```

> С флагом `-c` нельзя указать один `-o` для нескольких исходников: `gcc -c a.c b.c -o x.o` — ошибка.


> [!Зачем нужна раздельная компиляция]

- Каждый `.c` превращается в `.o` **отдельно**. Изменили один файл — перекомпилируете только его, остальные `.o` берутся готовыми. На этом построен `make`.
- Объектные файлы можно упаковывать в библиотеки и использовать повторно.
- Ошибки синтаксиса и типов находятся ещё до линковки.


> [!Пример компиляции файлов без линковки:]

```bash
gcc -Wall -Wextra -Werror -std=c11 -c main.c add.c mul.c
```

#### Что лежит внутри `.o`

Объектный файл содержит машинный код, данные и **таблицу символов**. Посмотреть её можно через `nm`:

```bash
$ nm main.o
                 U add
0000000000000000 T main
                 U mul
                 U printf

$ nm add.o
0000000000000000 T add
```

| Буква                       | Значение                                                                |
| --------------------------- | ----------------------------------------------------------------------- |
| `T`                         | символ **определён** в секции кода (функция)                            |
| `U`                         | символ **не определён** здесь (_undefined_), его должен найти линковщик |
| `D` / `B`                   | определённая глобальная переменная (с начальным значением / без)        |
| `R`                         | константы только для чтения                                             |
| строчная буква (`t`, `d` …) | символ локальный (`static`), снаружи файла не виден                     |

В `main.o` функции `add`, `mul` и `printf` помечены `U`: компилятор поверил прототипам и оставил «заглушки». Найти реальный код — задача линковщика.

#### Поиск заголовков

- `#include "calc.h"` — сначала в каталоге текущего файла, затем в путях из `-I`, затем в системных;
- `#include <stdio.h>` — в путях из `-I`, затем в системных каталогах (`/usr/include` и др.).

Список путей показывает команда:

```bash
echo | gcc -E -Wp,-v -x c -
```

#### Флаги компиляции

| Флаг                  | Назначение                                                       |
| --------------------- | ---------------------------------------------------------------- |
| `-I include/`         | добавить каталог поиска заголовков                               |
| `-D DEBUG`, `-D N=10` | определить макрос (как `#define`)                                |
| `-std=c11`            | версия стандарта                                                 |
| `-Wall -Wextra`       | набор предупреждений                                             |
| `-Werror`             | любое предупреждение = ошибка, сборка остановится                |
| `-pedantic`           | строгое соблюдение стандарта                                     |
| `-O0 -O2 -O3`         | уровень оптимизации                                              |
| `-g`                  | отладочная информация для gdb / valgrind                         |
| `-fPIC`               | позиционно-независимый код (нужен для динамических библиотек)    |
| `-MMD`                | сгенерировать `.d`-файл с зависимостями от заголовков для `make` |

#### Типичные ошибки

- `implicit declaration of function 'add'` — функцию вызвали без прототипа (забыли `#include` заголовка). В GCC 14 и новее это ошибка, в более старых — предупреждение.
- `expected ';' before ...` — синтаксис.
- `unused variable`, `unused parameter` — предупреждения `-Wall` / `-Wextra`.

Важно: **компилятор проверяет только то, что функция объявлена, а не то, что она существует**. Если реализации нигде нет, ошибка появится позже — на линковке (`undefined reference`).

### 4. Линковка (без флагов)

`ld` берёт один или несколько `.o`, а также библиотеки, и собирает из них **исполняемый файл**: связывает вызовы с определениями функций, назначает адреса и добавляет код запуска (`crt1.o`), который вызывает `main`. 

**Линковка (компоновка)** — последний этап: из объектных файлов и библиотек получается один исполняемый файл. Выполняет её **линковщик `ld`**, а `gcc` лишь запускает его с правильными аргументами.

```bash
gcc main.o add.o mul.o -o app
```

#### Про флаг `-o`

`-o` — это **не флаг линковки**, а просто «имя выходного файла». Он работает на любом этапе:

```bash
gcc -E main.c -o main.i   # результат препроцессора
gcc -c main.c -o main.o   # результат компиляции
gcc main.o -o app         # результат линковки
```

Если `-o` не указать, линковка создаст файл с именем `a.out`.

Линковку можно запустить и сразу из исходников. Тогда `gcc` сам создаст временные `.o`, слинкует их и удалит:

```bash
gcc main.c add.c mul.c -o app
```

#### Что делает линковщик

1. **Объединение секций.** Из каждого `.o` берутся секции и склеиваются по типам:

| Секция    | Что хранит                                                            |
| --------- | --------------------------------------------------------------------- |
| `.text`   | машинный код функций                                                  |
| `.rodata` | константы, строковые литералы                                         |
| `.data`   | глобальные переменные с начальным значением                           |
| `.bss`    | глобальные переменные без значения (нули, место только резервируется) |

2. **Разрешение символов.** Для каждого символа `U` (требуется) ищется определение `T`/`D` в других файлах или библиотеках. Если символ определён дважды — ошибка `multiple definition`, если ни разу — `undefined reference`.
3. **Релокации.** Теперь, когда известны итоговые адреса, линковщик правит в машинном коде места, где стояли «заглушки» (адреса вызовов и переменных).
4. **Запись результата.** Формируется исполняемый файл (ELF) с точкой входа `_start` из `crt1.o`. Именно `_start` готовит среду и вызывает `main`.

То есть до линковки `main.o` содержит «вызови `add`, адрес пока неизвестен», а после — реальный адрес.

#### Порядок аргументов

Линковщик обрабатывает файлы **слева направо**. Для `.o` порядок почти не важен, а для библиотек важен. Правило: **сначала объектные файлы, потом библиотеки**.

#### Частые ошибки линковки

| Сообщение                                    | Причина                                                                 | Что делать                |
| -------------------------------------------- | ----------------------------------------------------------------------- | ------------------------- |
| `undefined reference to 'mul'`               | нет реализации: забыли `mul.o` или библиотеку                           | добавить файл / `-l`      |
| `undefined reference to 'sqrt'`              | функция из отдельной библиотеки                                         | добавить `-lm` в конец    |
| `multiple definition of 'add'`               | одно имя определено в двух `.o` (например, функция в `.h` без `static`) | оставить одно определение |
| `cannot find -lcalc`                         | не найден `libcalc.a` / `libcalc.so`                                    | проверить имя и `-L`      |
| `undefined reference to 'main'`              | нет функции `main`                                                      | добавить её               |
| `collect2: error: ld returned 1 exit status` | не самостоятельная ошибка, а итог проваленной линковки                  | читать строки выше        |

# Линковка
## Правила поиска библиотек

Библиотеку можно указать двумя способами: **по имени** (`-l` + `-L`) или **прямым путём к файлу**.

### Флаги `-l` и `-L`

- **`-l<имя>`** — «подключи библиотеку с таким именем». К имени добавляется префикс `lib` и расширение: `-lm` → `libm.so` или `libm.a`; `-lcalc` → `libcalc.so` или `libcalc.a`. Пробела между `-l` и именем обычно нет.
- **`-L<каталог>`** — «ищи библиотеки ещё и в этом каталоге». Может повторяться.

```bash
gcc main.o -L./lib -lcalc -lm -o app
```

Символы `-I` и `-L` легко перепутать: **`-I` — для заголовков (этап компиляции), `-L` — для библиотек (этап линковки)**.

### Порядок поиска каталогов

1. Каталоги из `-L`, **в том порядке, в котором они указаны** в командной строке.
2. Каталог(и) из переменной окружения `LIBRARY_PATH` (если задана).
3. **Стандартные системные каталоги** (зашиты в `gcc` / `ld`): обычно `/usr/local/lib`, `/usr/lib`, `/lib`, а также каталоги с именем архитектуры вроде `/usr/lib/x86_64-linux-gnu`. Точный список зависит от системы.

Увидеть реальные пути на своей машине:

```bash
gcc -print-search-dirs               # строка libraries: =... — это пути поиска библиотек
gcc -print-file-name=libm.a          # где gcc нашёл конкретный файл
ld --verbose | grep SEARCH_DIR       # встроенные пути ld
```

В **каждом** просматриваемом каталоге линковщик сначала ищет `lib<имя>.so`, и только если его нет — `lib<имя>.a`. То есть по умолчанию **динамическая библиотека побеждает статическую**. Чтобы управлять этим:

| Как                                 | Эффект                                               |
| ----------------------------------- | ---------------------------------------------------- |
| `-static`                           | везде использовать только `.a` (включая libc)        |
| `-Wl,-Bstatic -lcalc -Wl,-Bdynamic` | только `libcalc` статически, остальное динамически   |
| `-l:libcalc.a`                      | точное имя файла, без подстановки `lib` и расширения |
| `./lib/libcalc.a`                   | просто путь к файлу, без `-l` и `-L`                 |

Первый каталог из `-L`, где найден **хоть какой-то** подходящий файл, останавливает поиск — следующие каталоги уже не смотрятся. Это значит, что при одинаковых именах побеждает тот каталог, который стоит **раньше**.

### Порядок указания библиотек

Линковщик читает аргументы **слева направо** и держит список ещё неразрешённых символов. Из **статической** библиотеки он берёт только те объекты, которые закрывают уже известные на этот момент `U`-символы. Поэтому:

```bash
gcc main.o -lcalc -o app   # правильно: main.o сначала
gcc -lcalc main.o -o app   # ошибка: undefined reference to 'add'
```

Если библиотека A использует функции библиотеки B, то порядок такой: `-lA -lB` (зависимая — раньше). Взаимно зависимые библиотеки можно обернуть в группу:

```bash
gcc main.o -Wl,--start-group -lA -lB -Wl,--end-group -o app
```

### Поиск на этапе запуска (для динамических библиотек)

Проверка `-L` касается только линковки. Динамическая библиотека ищется **ещё раз при запуске программы** загрузчиком `ld.so`:

| Когда    | Где ищется                                                                                                                                                 |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Линковка | `-L`, `LIBRARY_PATH`, системные каталоги                                                                                                                   |
| Запуск   | `RPATH`/`RUNPATH` (вшит в бинарник через `-Wl,-rpath,<dir>`), `LD_LIBRARY_PATH`, кэш `/etc/ld.so.cache` (обновляется `ldconfig`), затем `/lib`, `/usr/lib` |

Это частая причина ошибки `error while loading shared libraries: libcalc.so: cannot open shared object file` при том, что **линковка прошла успешно**. Для статических `.a` такой проблемы нет: код уже внутри бинарника.

## Виды библиотек

**Библиотека** — готовый набор функций (и данных), который можно подключать к разным программам. Интерфейс библиотеки — заголовочные файлы (`.h`), реализация — скомпилированный код. Бывает два вида: **статические** и **динамические**.

| Критерий                             | Статическая (`.a`)                       | Динамическая (`.so`)                                   |
| ------------------------------------ | ---------------------------------------- | ------------------------------------------------------ |
| Когда код попадает в программу       | при линковке (копируется)                | при запуске (подгружается)                             |
| Размер исполняемого файла            | больше                                   | меньше                                                 |
| Нужен ли файл библиотеки для запуска | нет                                      | да, и в правильном месте                               |
| Обновление библиотеки                | нужно **пересобрать** программу          | достаточно заменить `.so` (если интерфейс совместим)   |
| Память при нескольких программах     | у каждой своя копия кода                 | одна копия на всех                                     |
| Запуск                               | чуть быстрее (нет загрузки и связывания) | чуть медленнее                                         |
| Переносимость бинарника              | высокая: всё внутри                      | зависит от библиотек на целевой машине                 |
| Типичные проблемы                    | раздувание размера, дублирование кода    | `cannot open shared object file`, несовместимые версии |

### Статическая библиотека

- Файл `lib<имя>.a` (_archive_; в Windows — `.lib`). По сути это **архив объектных файлов** `.o` с индексом символов.
- Подключается **на этапе линковки**: нужные объекты **копируются внутрь** исполняемого файла.
- После сборки программа самодостаточна — файл `.a` для запуска больше не нужен.

### Динамическая библиотека

- Файл `lib<имя>.so` (_shared object_; в macOS — `.dylib`, в Windows — `.dll`).
- При линковке код **не копируется**: в бинарник записывается только информация «нужна `libcalc.so`, функции `add` и `mul`».
- Настоящая загрузка происходит **при запуске программы**: загрузчик `ld.so` находит файл, отображает его в память и связывает вызовы. Одна копия библиотеки в памяти может использоваться многими процессами.
- Собирается из объектов, скомпилированных с `-fPIC`, флагом `-shared`:

```bash
gcc -fPIC -c add.c mul.c
gcc -shared add.o mul.o -o libcalc.so
```

Большинство программ на C уже используют динамическую библиотеку: стандартную `libc.so.6` (проверьте: `ldd app`).

## Статические библиотеки

Статическая библиотека — это **архив** формата `ar`: контейнер, в котором лежат объектные файлы (`.o`) целиком, без сжатия, плюс **индекс символов**.

- Каждый `.o` внутри называется **членом архива** (_member_), со своим заголовком (имя, дата, размер, права).
- **Индекс символов** — служебный член, в котором записано «символ `add` определён в члене `add.o`». Его строит `ar` с ключом `s` или утилита `ranlib`. Благодаря индексу линковщик не читает весь архив, а сразу знает, какой объект взять.
- В `.a` **нет заголовочных файлов**. `calc.h` нужно хранить рядом и подключать через `-I`

### Утилита `ar`

```bash
ar <ключи> <архив> [файлы...]
```

|   |   |
|---|---|
|Ключ|Что делает|
|`r`|добавить файлы в архив, а существующие с тем же именем **заменить**|
|`c`|создать архив без предупреждения, если его ещё нет|
|`s`|создать/обновить **индекс символов** (то же, что `ranlib`)|
|`t`|показать список членов архива|
|`x`|извлечь члены из архива в текущий каталог|
|`d`|удалить член из архива|
|`v`|подробный вывод|

Стандартная команда создания: **`ar rcs libcalc.a add.o mul.o`**.

### Как линковщик берёт код из `.a`

Это главное отличие от обычных `.o`: **объектные файлы, указанные в команде, линкуются всегда целиком, а члены архива — только по необходимости.**

Алгоритм (упрощённо):

1. Линковщик держит список **ещё не разрешённых** символов (`U`) из уже обработанных файлов.
2. Встретив `.a`, он смотрит её индекс: есть ли там определение какого-либо из этих символов?
3. Если да — **этот член (и только он)** извлекается и добавляется в программу. Его собственные `U`-символы пополняют список.
4. Шаги 2–3 повторяются для **этого же архива** до тех пор, пока он может закрыть хотя бы один символ.
5. Дальше линковщик переходит к следующему аргументу и **к уже пройденным архивам больше не возвращается**.

Из этого вытекают важные следствия.

**Следствие 1. Порядок аргументов.** Архив должен стоять **после** файлов, которые от него зависят:

```bash
gcc main.o libcalc.a -o app      # работает
gcc libcalc.a main.o -o app      # undefined reference to 'add'
```

Когда линковщик дошёл до `libcalc.a`, в списке ещё не было ни одного `U`-символа (`main.o` не прочитан) — и ни один член не извлёкся.

**Следствие 2. Зависимости между библиотеками.** Если `libA.a` вызывает функции из `libB.a`, то порядок `-lA -lB`. Если библиотеки зависят друг от друга по кругу — используйте группу `-Wl,--start-group ... -Wl,--end-group` или укажите библиотеку дважды. Сам `.a` **не хранит** информацию о том, что ему нужны другие библиотеки, поэтому `-lm` и подобные всегда нужно указывать в команде самим.

**Следствие 3. Единица включения — объектный файл.** Если в одном `add.c` лежит 20 функций и вызывается одна, в программу попадёт **весь** `add.o`. Поэтому в библиотеках удобно делать небольшие `.c`-файлы по смыслу (в стандартной libc функции часто разнесены по отдельным файлам).

**Следствие 4. Приоритет собственных объектов.** Если вы сами определили функцию с тем же именем, что есть в библиотеке, и ваш `.o` стоит раньше архива, линковщик считает символ закрытым и член из `.a` не берёт. Но если этот член всё равно понадобится для другого символа — получите `multiple definition`.

**Следствие 5. Локальные функции не видны.** Функция с `static` (в `nm` — строчная `t`) существует только внутри своего `.o` и снаружи недоступна. Это нормальный способ спрятать вспомогательные функции библиотеки.

### Сборка статической библиотеки

Сборка — это два шага: **скомпилировать** исходники библиотеки в `.o` и **упаковать** их в архив.


> [!Шаг 1. Компиляция в объектные файлы]

```bash
gcc -Wall -Wextra -Werror -std=c11 -c add.c mul.c
```

Получатся `add.o` и `mul.o`. Флаг `-c` обязателен: линковки на этом шаге быть не должно (в библиотеке нет `main`).


> [!Шаг 2. Упаковка в архив]

```bash
ar rcs libcalc.a add.o mul.o
```

- `r` — добавить файлы в архив;
- `c` — создать архив, если его нет;
- `s` — построить индекс символов.

#### Правила имененования

- Для подключения через `-lcalc` файл должен называться **`libcalc.a`**: префикс `lib`, имя, расширение `.a`.
- Другое имя (например, `calc.a`) работает, но подключать его придётся **по пути к файлу**

#### Пример

Пользователю библиотеки нужны **два** артефакта: сам архив и заголовок.

```
project/
├── include/
│   └── calc.h        # интерфейс
├── lib/
│   └── libcalc.a     # реализация
└── main.c            # использует библиотеку
```

```make
CC      = gcc
CFLAGS  = -Wall -Wextra -Werror -std=c11
AR      = ar
ARFLAGS = rcs

LIB     = libcalc.a
LIB_OBJ = add.o mul.o

all: app

app: main.o $(LIB)
	$(CC) main.o -L. -lcalc -o $@

$(LIB): $(LIB_OBJ)
	$(AR) $(ARFLAGS) $@ $^

%.o: %.c calc.h
	$(CC) $(CFLAGS) -c $< -o $@

clean:
	rm -f *.o $(LIB) app

.PHONY: all clean
```

Что здесь важно:

- Цель `$(LIB)` зависит от `.o`-файлов; при изменении любого `.c` пересоберётся только он, а потом обновится архив.
- `$@` — имя цели (`libcalc.a`), `$^` — все зависимости (`add.o mul.o`).
- Цель `app` зависит от `$(LIB)`: изменили библиотеку — программа перелинкуется.
- Строки команд в Makefile начинаются с **символа табуляции**, а не пробелов.
- Команда `ar r` **не удаляет** члены, которых больше нет в списке. Если вы убрали файл из исходников, сделайте `make clean`, иначе его старый `.o` останется в архиве.

### Подключение своей `.a` при линковке

Допустим, у нас есть `include/calc.h`, `lib/libcalc.a` и `main.c`. Подключение состоит из двух независимых частей: **заголовок** нужен компилятору, **архив** — линковщику.

> [!Способ 1]
>  `-L` и `-l` (стандартный)

```bash
gcc -Wall -Wextra -Werror -std=c11 -I include -c main.c -o main.o
gcc main.o -L lib -lcalc -o app
```

- `-I include` — где искать `calc.h` (на этапе компиляции);
- `-L lib` — в каком каталоге искать библиотеку;
- `-lcalc` — найти `libcalc.a` (имя **без** `lib` и без `.a`).

Всё в одну строку, из исходника:

```bash
gcc -I include main.c -L lib -lcalc -o app
```

>Обратите внимание: `-lcalc` стоит **после** `main.c`, иначе линковщик не найдёт `add` и `mul`

---

> [!Способ 2. Прямой путь к файлу]

Архив передают как обычный входной файл. `-L` и `-l` не нужны, а имя может быть любым:

```bash
gcc main.o lib/libcalc.a -o app
gcc main.o s21_string.a -o app      # имя без префикса lib — тоже подойдёт
```

Этот способ **гарантированно берёт именно `.a`**, даже если в каталоге рядом лежит `libcalc.so` (при `-lcalc` выбрался бы `.so`).

---

> [!Способ 3]
> `-l:` с точным именем

```bash
gcc main.o -L lib -l:libcalc.a -o app
gcc main.o -L . -l:s21_string.a -o app
```

После `-l:` указывается имя файла целиком, и линковщик ищет его по каталогам `-L` и системным, не подставляя `lib` и расширение.

#### Какой способ выбрать

| Ситуация                                       | Способ                                                             |
| ---------------------------------------------- | ------------------------------------------------------------------ |
| Библиотека с именем `libXXX.a`, пути известны  | `-L<dir> -lXXX`                                                    |
| Файл называется не `libXXX.a`                  | путь к файлу или `-l:имя.a`                                        |
| Рядом лежат `.so` и `.a`, нужна именно статика | путь к файлу, `-l:libXXX.a` или `-Wl,-Bstatic -lXXX -Wl,-Bdynamic` |
| Несколько библиотек                            | `-lA -lB -lm`, зависимые раньше                                    |

#### Итоговая схема

1. `gcc -c add.c mul.c` — получить объекты библиотеки.
2. `ar rcs libcalc.a add.o mul.o` — собрать архив.
3. `gcc -I include -c main.c` — скомпилировать программу, заголовок через `-I`.
4. `gcc main.o -L lib -lcalc -o app` — слинковать с библиотекой, архив после объектов.
5. `./app` — запустить; файл `libcalc.a` больше не нужен.
